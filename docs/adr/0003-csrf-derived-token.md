# 0003 · CSRF 令牌由会话令牌哈希派生

日期：2026-10-18
状态：已采纳

## 背景

契约要求双提交（§5 / §9）：`GET /auth/me` 下发明文 `csrf_token`，服务端存 `csrf_hash`，
写请求带 `X-CSRF-Token`。`sessions` 表因此有 `csrf_hash` 列。

朴素实现有两个麻烦：

1. **不能存明文**，所以每次 `me` 都得重新生成令牌并覆盖哈希 —— 多个标签页/并发请求会互相失效。
2. 若把令牌放内存缓存，则与"会话信息只在 SQLite"相冲突，进程重启后失效。

## 选项

1. **每次 `me` 轮换**：实现最直白，但并发下 403 频发，且刷新页面才恢复。
2. **明文存库**：破坏"服务端只存哈希"的安全属性。
3. **由会话令牌哈希做 HMAC 派生**（本决定）：
   `csrf = HMAC-SHA256(pepper, "csrf|" + session.token_hash)`。
   浏览器不需要能自己算出它（cookie 是 HttpOnly），服务端则随时可复算。

## 决定

采用 3：

- `pepper` 就是 `settings.visitor_salt`（每库随机、启动时注入 `utils`）。
- `sessions.csrf_hash = sha256(csrf)` 仍然写入，保留契约列与纵深防御。
- 中间件校验时用请求头值与**重新派生**的期望值做常量时间比较；不读库里的 `csrf_hash`。

## 后果

- CSRF 令牌在整个会话生命周期内稳定，多标签页不会互相踢掉；不需要轮换逻辑。
- 令牌与会话强绑定：登出/换会话即失效，无需额外清理。
- 若 `visitor_salt` 被重置，所有在途的 CSRF 令牌同时失效（用户刷新页面即可恢复），
  但**不会**使会话 cookie 失效。
- 想改成真正的随机令牌时，只需改 `utils.CSRFToken` 与中间件，表结构不用动。
